# Fork-Local Core Edits

Read before editing Piwigo core, a core theme or a root entry, and before pulling from upstream.
Every edit this fork makes outside `plugins/` is listed here, one bullet each; a new one is added in
the same commit that makes it. An upstream pull checks each bullet still holds after the merge.

- Two fork-local `trigger_notify()` calls have been added to core so the provenance plugin can hook the paths that create album links. Upstream has neither:
  - `associate_images_to_categories` in `admin/include/functions.php`, inside the `if (count($inserts))` block — the funnel every virtual link goes through (API, Batch Manager, upload). Fired once per album that got a new link, with only the photos newly linked to it, so a photo already in an album never inherits from it again (task 20 of change `2026-10-15-exploratory-testing-answers`). Payload: `image_ids`, `category_ids` (one id)
  - `site_update_associate_images` in `admin/site_update.php`, after the `$insert_links` `mass_inserts()` — the filesystem sync inserts its storage links directly without calling the helper. Payload: the `$insert_links` rows. This is the **only** trigger in that file; anything claiming it fires none is out of date
- One fork-local core fix: album thumbnails no longer count an admin's empty sub-albums, which the listing hides (`discount_hidden_subalbums()`, `include/category_cats.inc.php`), see [decision 0037](../../docs/agents/decisions/0037-album-thumbnails-count-only-listed-subalbums.md)
- One fork-local core fix: `set_cat_visible()` (`admin/include/functions.php`) ends with `invalidate_user_cache()`, so closing or reopening an album (Geschlossenes Album, `pwg.categories.setInfo`) takes effect for visitors at once instead of after the next cache purge. Tested by provenance's `CoreAlbumLockTakesEffectTest`
- One fork-local root entry: `handbuch.php` serves `handbuch/` to logged-in users only, rewritten from `/handbuch/*` by `.ddev/nginx/handbuch.conf` and `handbuch/.htaccess` ([decision 0063](../../docs/agents/decisions/0063-the-handbook-is-served-through-a-login-checking-entry.md))
- One fork-local core template change: the merge panel's two buttons in `admin/themes/default/template/tags.tpl` pass through `|@translate` (upstream hard-codes English `Confirm merge` / `Cancel`). It stays fork-local: nothing is ever pushed or proposed to `Piwigo/Piwigo` ([git-and-commits.md](git-and-commits.md))
- The `modus` theme carries one fork-local change: fit-to-area and zoom on the picture page (`js/photo.zoom.js`, a changed `rvas_choose()`), see [decision 0032](../../docs/agents/decisions/0032-modus-picture-fit-and-zoom-is-a-fork-local-theme-edit.md)
- One fork-local `trigger_notify()` for `plugins/photoedit`: `add_uploaded_file_before_replace` in `add_uploaded_file()` (`admin/include/functions_upload.inc.php`), just before `delete_element_files()` removes the photo a replace overwrites. Payload: `image_id`, the photo's `path`. Every caller that passes an `image_id` (Fotos hinzufügen's replace through `pwg.images.upload` update mode, `pwg.images.addFile`, `pwg.images.addSimple`) goes through it; photoedit copies the file first ([decision 0072](../../docs/agents/decisions/0072-a-replace-is-copied-through-a-core-trigger.md))
- One fork-local core fix: `get_tag_ids()` (`admin/include/functions.php`) puts a typed tag name into Unicode NFC (`Normalizer::FORM_C`, skipped without the intl extension) before `tag_id_from_tag_name()`, so a name typed decomposed links the tag stored composed instead of creating a second one of the same visible name. Core's `url_name` fallback stays; only typetags' `addNewTag` drops it. Tested by provenance's `CoreTypedTagNameCharacterizationTest`
- One fork-local core script change: `admin/themes/default/js/tags.js` shows a refused `pwg.tags.delete` or `pwg.tags.merge`'s own message in the screen's error line (single delete, multiple delete, merge), and the multiple delete no longer treats every answer as success (`stat = 'ok'` was an assignment). Upstream shows *A problem has occured* or nothing. Needed for persons' refusal to delete a person's tag (task 18 of change `2026-10-15-exploratory-testing-answers`); tested by persons' `admin-tag-guard.spec.js`
- One fork-local core fix: the menu photo count (`nb_total_images` in `getuserdata()`, `include/functions_user.inc.php`) joins `images` and `categories`, so a link left behind by a deleted photo or album no longer counts ([decision 0074](../../docs/agents/decisions/0074-the-menu-photo-count-ignores-dead-links.md)). Tested by provenance's `CoreMenuPhotoCountTest`
- Fork-local changes to the tag screen (task 26 of change `2026-10-15-exploratory-testing-answers`, [decision 0076](../../docs/agents/decisions/0076-the-unused-tag-cleanup-keeps-coloured-and-person-tags.md)): `admin/themes/default/template/tags.tpl` translates `str_number_photos` and adds `str_number_photo`, and renders the menu's server-side count with `translate_dec`; `admin/themes/default/js/tags.js` picks the singular for 1 (`photoCountText()`), lists the unused tags one per line, shows a refused rename through `showError()` and gives a Duplikat its `raw_name`; `get_orphan_tags()` (`admin/include/functions.php`) passes its rows through the `get_orphan_tags` `trigger_change()`, which `plugins/galleryrules` uses to drop colour-group and person tags. Tested by provenance's `CoreOrphanTagsCharacterizationTest` and galleryrules' `OrphanTagsTest` and `tag-admin.spec.js`
- Fork-local album properties changes (task 35 of change `2026-10-15-exploratory-testing-answers`): `admin/themes/default/js/cat_modify.js` runs `pwg.categories.setInfo`, then `pwg.categories.move`, and shows the confirmation only when both succeeded (a refused move shows the server's message, and the parent field goes back to the saved one; upstream sent both at once and always said "Album updated"); the info box's "Modified" card shows the string once (upstream wrote it into both of its lines). `admin/themes/default/js/album_selector.js` does not offer the sub-albums of `currentAlbumId`, in the browsable list or the search, and shows no expander on that album. Tested by provenance's `CoreAlbumMoveCharacterizationTest` (the server half) and `album-properties.spec.js`
- Fork-local upload changes (task 27 of change `2026-10-15-exploratory-testing-answers`, [decision 0079](../../docs/agents/decisions/0079-upload-chunks-are-per-user-and-abbrechen-cleans-up.md)): `ws_images_upload()` in `include/ws_functions/pwg.images.php` keys the buffer by user and file name, opens it `wb` at chunk 0 and removes a `.part` older than a day; new method `pwg.images.uploadCancel` (`ws.php`, same file) removes the chunks and lounge photos of a cancelled upload; `admin/themes/default/js/photos_add_direct.js` reports a non-JSON or refused answer, a failed `uploadCompleted` and an Abbrechen before the first file; `admin/themes/default/template/photos_add_direct.tpl` passes two existing admin strings to it. Tested by provenance's `CoreUploadChunkIsolationTest` and galleryrules' `upload-page.spec.js`
- Fork-local modus theme changes (task 37 of change `2026-10-15-exploratory-testing-answers`, extending [decision 0032](../../docs/agents/decisions/0032-modus-picture-fit-and-zoom-is-a-fork-local-theme-edit.md)): `themes/modus/css/base.css.tpl` gives `.additional_info`, `.titrePage H2`, the tag list's links and the selected-tag chips `overflow-wrap: anywhere`, so a long album-description word or a 255-character tag name breaks instead of widening the page; `themes/modus/js/photo.zoom.js` subtracts `#theImage`'s padding-bottom from the `max-height` it sets, so the zoomed photo's horizontal scroll bar ends inside the window. Tested by provenance's `long-words.spec.js` and persons' `picture-zoom-scrollbar.spec.js`. The phone layout of the tag letter list is not covered. Task 48 changed `#fullTagCloud SPAN` in `themes/modus/css/tags.css` from `white-space: nowrap` to `white-space: normal; overflow-wrap: anywhere`, so a 255-character tag in the cloud wraps instead of widening the page (short tags still break only at spaces); tested by provenance's `long-words.spec.js`
- Fork-local album delete changes (task 43 of change `2026-10-15-exploratory-testing-answers`): `admin/themes/default/js/cat_modify.js` shows a refused `pwg.categories.delete`'s message (decision 0083's 409) in the footer's error line and keeps the album; `admin/themes/default/js/albums.js` shows it in the delete dialog's `.DeleteAlbumErrors`, which stays open and is hidden again when the dialog is next opened. Upstream only `console.log`s the failure. Tested by galleryrules' `album-delete-refusal.spec.js`
- Fork-local API and sync-count fixes (task 36 of change `2026-10-15-exploratory-testing-answers`): `ws_categories_getList()` (`include/ws_functions/pwg.categories.php`) answers the substitute's id as `representative_picture_id` when the stored one is above the viewer's level, `null` when there is none; `ws_images_setInfo()` (`include/ws_functions/pwg.images.php`) refuses a `level` outside `available_permission_levels` with `WS_ERR_INVALID_PARAM` before anything is read, as `setPrivacyLevel` does (a value above the maximum never reaches it: `ws.php` clamps it); `admin/site_update.php` counts the photos of removed folders in "photos deleted" (counted before `delete_categories()`, simulation too; the file pass adds to it) and assigns `update_result` after the metadata pass, so "errors" equals the listed ones. Tested by provenance's `CoreApiAnswersCharacterizationTest` and `CoreSiteUpdateCountsCharacterizationTest` (the [ERR] cases there are the unchanged behaviour, the [REQ] cases the fixes) and photoinfo's `CoreEditTest`. Task 47 (same change) extends the `level` check to `pwg.images.upload`, `addSimple`, `add` and `uploadAsync` in the same file (`Invalid level` before anything is stored); tested by provenance's `CoreUploadLevelCharacterizationTest`. The sync's deleted-photo count needed no further change: `delete_categories()` deletes only photos stored in the removed folders, which is what the count already covers
- Fork-local Batch Manager unit mode change (task 40 of change `2026-10-15-exploratory-testing-answers`): `admin/themes/default/js/batchManagerUnit.js` shows a refused `pwg.images.setInfo`'s own message inside the photo's error badge (`showErrorLocalBadge(pictureId, message)`); upstream shows only *An error has occured*. Needed for persons' refusal to take a marked person's tag off a photo. Tested by persons' `admin-batch-unit-guard.spec.js`
- Fork-local sync change (task 51 of change `2026-10-15-exploratory-testing-answers`, [decision 0085](../../docs/agents/decisions/0085-the-sync-links-a-stray-photo-to-a-remaining-album.md)): `admin/site_update.php` calls `relink_photos_of_albums_to_be_removed()` (new, `admin/include/functions.php`, with `get_unsorted_album_id()`) before `delete_categories()`, so a photo stored elsewhere whose only links were in a removed folder's album is linked to the parent of the highest removed album, or to a private root album `Ohne Album`; the result list gets one line (`site_update.tpl`, `NB_RELINKED`). Tested by provenance's `CoreSiteUpdateCountsCharacterizationTest`
