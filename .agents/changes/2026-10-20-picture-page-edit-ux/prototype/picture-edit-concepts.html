Fotoseite bearbeiten: drei Konzepte zum Ausprobieren

Today the picture page has four edit features with four different save rules. Below are three ways to make them one consistent thing. Each concept has a working mockup (sample photo and data, nothing is sent anywhere), a list of what to try, and the reasoning behind it.

What the page does today

FeatureHow you startWhen it is savedHow you finish
Datum (photoinfo)Click the text (hidden affordance, tooltip only)Speichern buttonSpeichern / Abbrechen, then page reloads
Info (photoinfo)Click the textSpeichern buttonSpeichern / Abbrechen, then page reloads
Personen (persons)Button „Personen markieren“ below the info tableimmediately per box after naming; × deletes with no confirmButton changes to „Markieren beenden“; reload if anything changed
Schlagwörter (typetags)Nothing to start; „+ name“ badges always shownimmediately on one clickNothing; no reload, no confirmation shown

So the same page asks the user to learn: click-the-text, a start/stop toggle, instant one-click writes, and a full-screen mode. Every one of them writes into the image file (exiftool), so even the „instant“ ones take a moment and can fail.

Idea: the page has two states, Ansehen and Bearbeiten. One big button switches to Bearbeiten. Then everything is editable at once: date, info, tags, and drawing faces on the photo. Nothing is written until the user presses Speichern in the orange bar. This is the model of a paper form: fill in, then hand in.

Try this
  1. Press Foto bearbeiten. Note the orange frame and the bar on top (two signals for the mode).
  2. Change the year, remove the tag „Kirmes“, add „Kirche“, drag a box around the third person's head and name it.
  3. Watch the change counter. Press Abbrechen or Nächstes Foto → to see the „lose changes?“ question.
  4. Press Speichern.

Pros

  • Simplest rule to explain: „Bearbeiten drücken, ändern, Speichern drücken.“
  • The mode is shown twice (frame + bar), as NN/g asks for modes.
  • No accidental writes: a misclick on a tag in view mode does nothing.
  • One reload at the end instead of one per feature.

Cons

  • Work can be lost: navigate away, session expires, browser closes. Needs a leave-warning (beforeunload).
  • Speichern runs several file writes in a row (date, info, tags, regions). If one fails, the message must say which part was not saved. Harder to explain than one failure.
  • Two users editing the same photo: the second Speichern overwrites more.
  • Drawing on the photo is active during the whole mode, so zoom and the photo's prev/next click zones are off while editing.

Seen in

Form-style „Edit → Save“ pages; Wikimedia Commons (edit, then Publish). Photo apps rarely make the whole info panel one mode.

Effect on the code

  • Largest change. A new shared editor script owns the mode; photoinfo, typetags and persons stop saving on their own and hand their changes to it.
  • typetags and persons need „staged“ changes (kept in the browser until Speichern).
  • Save = sequence of existing ws calls (pwg.photoinfo.setDate, setInfo, typetags.image.addTag/removeTag, pwg.persons.addRegion/deleteRegion), or one new combined method that takes the persons lock once.
  • photoedit stays its own tool (it replaces the file).

Idea: keep „it saves by itself“, but make it the rule everywhere and make it visible. Every step is complete in itself: pick a tag, finish a date, name a face. Right after, the row shows ✓ Gespeichert · Rückgängig, and a list at the bottom shows the last changes with an undo for each. Marking a person becomes one action („+ Person markieren“, draw, name, done), with no start/stop.

Try this
  1. Click „+ Kirche“. See the status on the row. Open „Letzte Änderungen an diesem Foto“ (closed by default), which names who changed what and when. Press Rückgängig. Switch the role in the grey bar: a normal user can undo only their own changes, an administrator can undo everyone's.
  2. Press ✎ ändern at Datum, change „ca.“ to „vor“: saved at once. Change the year and press Enter or leave the field.
  3. Type in Info: the row says „noch nicht gespeichert“ until you leave the field.
  4. Press + Person markieren, drag a box, choose a name. The mode ends by itself. Delete a box with ×, then undo it.

Pros

  • Closest to today: tags and persons already save at once. Least to learn for current users.
  • Nothing is ever lost by navigating away.
  • Undo instead of confirm dialogs (NN/g, GNOME HIG: users click through confirms; undo is the better net).
  • Each write is small, so a failure names exactly one thing.

Cons

  • Autosave of text is what the research warns about: users cannot tell „saved“ from „not saved“ (Primer, saasui). The status text has to carry all the trust.
  • Every keystroke-pause or field-leave writes the image file; many file writes, and „Rückgängig“ is one more.
  • A misclick on a tag is a real write (with undo). Older users may not notice it happened.
  • Undo of a person box creates a new region (new id); undo after somebody else changed the photo is ambiguous.

Seen in

Apple Photos captions (type in place), Google Docs-style autosave, Primer's rule „autosave only for toggle-like controls“ fits the tags but not the text fields.

Effect on the code

  • Smallest server change: all ws methods exist.
  • photoinfo: drop Speichern, save on field change/leave, no reload; add the status line.
  • persons: replace the toggle with a one-shot „+ Person markieren“; keep immediate save.
  • New: a per-page change list with undo (client side; undo re-sends the old value).

Idea: one pattern, repeated on every row. Each row (Datum, Info, Personen, Schlagwörter, Foto) has the same visible ✎ Bearbeiten button. It opens only that row, in orange, with the same footer: Abbrechen and Speichern. While one row is open, the other Bearbeiten buttons are off, so there is never a question of what Speichern will save. Opening Personen makes the photo drawable, with the same orange frame.

Try this
  1. Press ✎ Bearbeiten at Schlagwörter. Add and remove tags (shown dashed until saved). Press Speichern.
  2. Press Bearbeiten at Personen: the photo gets an orange frame. Drag a box round the third head, name it, delete another with ×. Abbrechen restores everything.
  3. Open Datum and try to open Info at the same time.

Pros

  • One rule, learned once, used five times: „Bearbeiten → ändern → Speichern“. Matches explicit save for text (Primer, Oracle Alta).
  • Face marking is a bounded mode with a clear start and a big Speichern, like Google Photos (Edit → Done), Flickr, digiKam.
  • Small units: little to lose, and an error belongs to the open row.
  • Visible button instead of „click the text“: better for users who do not hover to discover.

Cons

  • Tags take two clicks more than today (Bearbeiten, Speichern) for a single tag.
  • Five Bearbeiten buttons make the panel look busier in view mode.
  • Still a page reload or partial refresh after each Speichern, unless rows update in place.

Seen in

Google Photos (People: Edit → Done; date: pencil → dialog → Save), Flickr („Edit tags“ / „Edit people“ → Done), Atlassian inline edit with confirm/cancel next to the field, GOV.UK „Change“ links on summary rows.

Effect on the code

  • Medium. photoinfo already works this way (form + Speichern/Abbrechen); only the trigger becomes a visible button.
  • typetags: badges move into an edit section; Speichern sends the add/remove calls (or one new batch method, so the file is written once).
  • persons: the toggle becomes the row's Bearbeiten; regions are staged and sent on Speichern.
  • A tiny shared script makes sure only one row is open (also stops photoedit and persons fighting, which photoedit's editor.js handles ad hoc today).

My recommendation: C, with B's status line

The users are mostly older club members working through scanned family photos. The research points the same way on every count: explicit save for text, a clearly bounded mode for faces, one pattern per page, and status shown next to the control rather than in a passing toast. C gives that with the smallest risk of lost or unnoticed changes, and it maps onto the plugins as they are: one row, one ws method, one file write, one error message.

From B I would keep the persistent „✓ Gespeichert“ on the row after saving. From A I would keep the double mode signal (orange frame plus colored row) for the Personen row.

Applies to all three

  • Drehen/Zuschneiden stays its own full-screen tool: it replaces the file and can cut regions away, so it keeps its confirm step (the only irreversible action here).
  • One wording everywhere: Bearbeiten, Speichern, Abbrechen. Today there is also „Hinzufügen“, „Personen markieren“, „Markieren beenden“.
  • Targets at least 44 px; errors next to the field that caused them (NN/g, older adults).
  • The date keeps typed partial input („ca. 1955“) instead of a calendar picker (NN/g: „Why won't they just let me type the time?“).

Research sources

„fetched“ = page read in full; „snippet“ = only the search-result excerpt was available.

  • GitHub Primer: Saving fetched — start with explicit save; do not mix save patterns in one form; autosave only for toggle-like controls; text inputs need explicit save so a misclick is not silently submitted.
  • NN/g: Modes in User Interfaces fetched — poorly signalled modes cause errors; use at least two visual indicators for an active mode.
  • NN/g: Confirmation Dialogs fetched — confirm only serious, irreversible actions; undo is the main safety net.
  • NN/g: Usability for Older Adults fetched — small targets are a major barrier; inflexible inputs punish users; put errors where they are noticed and easy to fix.
  • Google Photos: label faces fetched — Info → People → Edit → change → Done.
  • Oracle Alta: Save Model snippet — explicit save gives an obvious outcome; keep button labels consistent.
  • saasui.design: autosave states snippet — „silent autosave is a trust trap“; autosave needs a visible Saving/Saved state.
  • Apple Photos: Info window snippet — caption typed in place; date via a dialog with an Adjust button.
  • Flickr Help, people and tags (flickrhelp.com, page refused automated access) snippet — „Add people“ / „Edit tags“, each finished with Done.
  • digiKam: People view snippet — face tags stay unconfirmed until the user confirms them.
  • FamilySearch: tag memories snippet — draw box, type name with suggestions, save per tag.
  • GNOME HIG: Dialogs snippet — users click through confirmations; prefer undo.
  • MDN: beforeunload snippet — attach only while changes are unsaved; the text cannot be customised.
  • Atlassian: Inline edit snippet — confirm/cancel next to the field; covers text, select, date.
